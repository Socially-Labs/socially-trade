# Account notification delivery

Migrations `038_notification_delivery.sql` and `039_wallet_notification_recovery.sql` add user-local stream cursors, nullable fund scope, finalized wallet receipts, device bindings and a durable push queue. Apply migrations before deploying the API and worker, then rebuild the APK. Legacy `after`/`before` requests still use notification IDs and exclude account-only wallet records so older apps can keep parsing fund-scoped events; new clients use `cursorVersion=2`, `afterCursor` and `beforeCursor`.

## Foreground

`/v0/ws` authenticates with a Privy token in a frame, never a URL. The APK subscribes to `account.notifications` with `cursorVersion:2`. PostgreSQL `NOTIFY` wakes subscribed gateways after commit; gateways send an invalidation, and the APK drains ordered REST pages from `/v0/me/notifications?afterCursor=...`. A 15-second server reconciliation detects lost LISTEN messages. The APK retries WebSocket connections with exponential jitter, renews authentication before expiry, closes the socket in background, and polls every 25 seconds only when disconnected. Resume always fetches missed records. Initial load shows saved inbox history without replaying historical toast animations. Toast queue is bounded to 20; all records remain in the inbox. Multiple event types share this one notification socket; market/dashboard streams remain separate existing transports.

`stream_sequence` is allocated under a per-user database row lock until commit. Notification identity IDs remain stable for read/detail links, but are not replay watermarks. Duplicate outbox fanout is protected by `(outbox_event_id,user_id)` uniqueness. Inserts target recipients in user ID order to reduce lock inversion. Read and detail routes require the recipient's authenticated account.

## Push and native setup

1. Apply migrations 038–039, deploy API plus worker, and configure an EAS project for `com.socially.trade`.
2. Set APK `EXPO_PUBLIC_EAS_PROJECT_ID` and build-time `GOOGLE_SERVICES_JSON`; configure FCM v1 credentials in EAS (and APNs for iOS). Never commit Firebase/service-account credentials. Build a new native development or release APK; Expo Go cannot verify Android remote push.
3. Configure Expo enhanced push security and server-only `EXPO_ACCESS_TOKEN`; set worker `NOTIFICATION_PUSH_ENABLED=true` after credentials work.
4. In Settings, select **Enable push notifications**. Permission is requested by this action. Existing grants refresh registration on foreground resume and token rotation.

A token belongs to one installation and account at a time. Explicit logout revokes it before clearing auth when the network is available and dismisses local notifications. Offline logout cannot contact the server: lock-screen content is always generic, bindings expire after 30 days without refresh, and the next account registration replaces the binding. Queued deliveries snapshot the target token/account; revoked, expired and reassigned bindings fail closed at claim time. A push already accepted by the OS cannot be recalled, so its payload has no financial text and the app verifies the current account before opening a notification. Foreground OS banners are suppressed in favor of the pearl toast.

The worker leases up to five jobs and sends concurrently, retries transient errors with exponential jitter, stores Expo ticket IDs, checks receipts after 15 minutes, revokes `DeviceNotRegistered`, and records terminal failures after 12 failed attempts. Delivery is at least once: a crash between remote acceptance and saving a ticket can resend. The app deduplicates by notification ID. `delivered_at` means Expo's receipt was successful; it does not mean the user read the alert. Monitor failed jobs and old pending jobs; invalid credentials must be fixed before requeuing terminal failures.

## Wallet receipts

Set API `WALLET_NOTIFICATIONS_ENABLED=true` with a reliable `SOLANA_RPC_URL`/`DEVNET_RPC_URL`. Registration at `PUT /v0/me/wallet-notifications` accepts only a Privy-linked wallet verified server-side. The observer checks the devnet genesis hash and subscribes to confirmed and finalized account changes over Solana WebSocket RPC. Set `SOLANA_WS_URL` if the provider uses a separate WebSocket endpoint; otherwise web3.js derives it from the HTTP RPC URL. A database/schema-scoped PostgreSQL advisory lock elects one API replica to own the RPC subscriptions. Gateways on every replica receive private PostgreSQL invalidations. The leader reconciles its subscription registry every 30 seconds and on wallet registration. Finalized changes wake a targeted receipt scan immediately; a fair 15-second recovery scan preserves catch-up after missed RPC events. Registration baselines the wallet address, its canonical USDC associated token address (even before that account exists), and existing USDC token accounts; each has an independent cursor. It watches up to 32 addresses per wallet, scanning at most 20 addresses per batch fairly. Register again to discover newly created noncanonical token accounts. This observer deliberately supports the app's devnet SOL and configured devnet USDC, not arbitrary mints or mainnet.

Only successful external System Program SOL transfers and SPL USDC transfers with verified destination owner/mint produce receipts. Transactions signed by the receiving wallet are excluded to avoid labelling swaps/internal activity as external deposits. CPI instructions are included. Receipts deduplicate `(network,signature,instruction-index,user)`, then append an account event and outbox record atomically with advancing the address cursor. Each address processes at most 50 signatures per scan with batched transaction reads. Separate persisted backfill and head cursors let large outages recover over multiple cycles without skipping arrivals during recovery. Missing transactions retain progress and surface scanner errors. The RPC must retain transaction history covering the outage; use archival RPC and alert on scanner errors. The scanner never credits paper cash or vault balances.

Confirmed account changes send an amount-free `wallet.updated` hint over the existing authenticated `account.notifications` channel only to the recipient. The visible wallet reads SOL and USDC at confirmed commitment on this hint, on focus/resume, manual refresh and after an app transaction. Reads coalesce while in flight; an invalidation during a read schedules a follow-up. Wallet balance and paper funding recovery polls run every 60 seconds while the screen is focused; neither queries offscreen. Price valuation refresh is independent. Receipt arrivals also invalidate balances. Hints never create receipts or credit balances: the received toast waits for verified finalized transfer parsing and durable outbox delivery, so chain finality and worker/RPC latency still apply.

The pearl toast has no close icon. A deliberate left/right swipe or fast flick dismisses it, a short drag returns it to rest, and tapping opens its detail. Dragging pauses automatic dismissal. Assistive technology retains a dismiss action and escape support.

The UI displays exact token quantities from integer amounts and identifies devnet. It does not invent a dollar value. Add valuation only with a persisted source price and valuation timestamp.

Tests cover account isolation, deduplicated fanout, identity IDs committing out of order, v2 REST replay, authenticated WebSocket wakeups, push tickets/receipts/backoff/revocation, finalized transfer parsing, scanner deduplication, single-leader RPC subscriptions, confirmed hints without invented receipts, immediate finalized scans and account-private wallet wakeups. ## Missing deposit toast troubleshooting

An in-app toast does not require Firebase, OS notification permission or a USB connection. It does require an enabled API observer, a successfully registered wallet, a running outbox worker, and a foreground app connected to that API. `GET /v0/me/wallet-notifications` returns the authenticated account's runtime enablement and watch status. The API logs `Wallet notification observer started` at startup. Changing `.env` requires restarting the API; the app retries failed registration every 15 seconds while active and exposes failures in the notification inbox instead of hiding them. Retry also attempts registration immediately.

Registration establishes a finalized baseline. Transfers completed before the wallet was registered are not automatically replayed as new alerts. Trace such a transfer by its devnet signature before deciding whether to backfill it. Wallet registration and receipt counts in a local database do not verify a phone connected to a different deployed API.
